## Why `/api/health` can return 503

- `lib/ops/health.ts:176-199,355-377` evaluates database, Redis, worker, queues, circuits, canary, storage, models, backup, restore, deployment, and critical-error checks together. Any `status: "fail"` makes the report `unhealthy` and `ok: false`.
- `app/api/health/route.ts:167-171` translates every non-healthy report to external `status: "degraded"`, but still returns HTTP **503** whenever `report.ok` is false; `operationalStatus` preserves `unhealthy`. Thus the top-level label can obscure a genuine failed check without changing the 503.
- Development can intentionally disable only the real-provider canary: `lib/worker.ts:5936-5946` records `disabledSchedulers.canary` if no positive `CANARY_ACCOUNTING_TEAM_ID` is configured outside production/staging/certification, and continues. `server/worker-process.ts:164-177` permits this one narrow dev-only readiness exception but deliberately does **not** start the worker heartbeat. That is intentional non-readiness, not proof the other workers are broken.
- The health aggregation does not honor that exception: `worker-readiness.ts:134-148` recognizes it, but `health.ts:220-226` fails any unready worker or missing heartbeat; `health.ts:264-274` independently fails a never-run/stale canary. `canary-worker.ts:186-202` specifically treats never-run as failed/stale. So intentional dev canary omission alone can contribute two failed health checks and a 503. A configured canary is scheduled daily at 06:00 UTC (`worker.ts:5957-5984`); after startup there may be no result until its scheduled run.
- There are other default-policy contributors: `capabilityPolicyFromEnv()` defaults media/storage, backup, and models to required (`health.ts:79-87`). In non-production, backup/restore status paths default to absent (`route.ts:114-123`), and missing required status evidence fails (`health.ts:292-325`). Storage is required by default and `checkStorage()` defines configured as all four DO Spaces values, regardless of the separate Replit object-storage indicator (`route.ts:56-81`). Therefore a dev 503 can be policy/configuration—not a DB outage. Conversely, DB/Redis probe failures, stale/missing heartbeat outside the narrow dev case, scheduler-registration omissions, open circuits, queue thresholds, model readiness failure, or actual failed/stale canary are substantive operational faults. Inspect each `services.*` status/message and `operationalStatus`; do not infer root cause from the 503 alone.
- Production/certification/staging require accounting configuration (`worker-readiness.ts:118-132`): an explicitly selected positive integer `CANARY_ACCOUNTING_TEAM_ID`. The worker validates it before registering provider-backed canary work and explicitly prohibits choosing an arbitrary/synthetic customer (`worker.ts:5954-5956`; `canary-worker.ts:259-274,307-310`). A human with accounting authority must designate a legitimate controlled owner/team; I am not nominating one. The real canary performs text and image generation (`canary-worker.ts:296-340,454+`), so an actual fresh pass is not a non-paid verification.
